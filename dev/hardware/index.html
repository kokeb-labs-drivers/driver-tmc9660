Hardware¶

The TMC9660's package, pins, bus settings, timing and power, as the driver uses them. The chip is a 70 V smart gate driver with a servo controller (FOC) in hardware and a buck converter; the driver talks to its processor over SPI or UART, never to the power stage directly.

Datasheet sections this page relies on

From Analog Devices (Trinamic) 19-101926 1:

  • Package, pins and power-up pin functions: Pin Configurations; Pin Descriptions, p. 11
  • Supply ranges and the hibernation mode: Power Supply - Electrical Characteristics, p. 17
  • Pin functions at power-up and the UART and SPI of the bootloader: General-Purpose Input/Output Description, p. 19
  • Clock, reset, DRV_EN, WAKE and FAULTN: Clock and Control Description, p. 63

All of them, with the driver API for each: Datasheet map.

Package and pins¶

The TMC9660 is sold in one package, the 64-pin TQFN (9 x 9 mm, 0.5 mm pitch) with an exposed pad that is GND. The pin table below is drawn from docs/hardware.yml, which cites the datasheet for each pin.

Which pins carry the host link¶

At power-up the bootloader selects the interface from the first valid command it sees on either bus, and the pin functions below replace the plain GPIO functions of the same pins (datasheet, General-Purpose Input/Output Description). A boot configuration written with BlWriteConfig() can move them.

Interface Pins Notes
UART GPIO6 (pin 62) is UART_TX, GPIO7 (pin 63) is UART_RX The bootloader detects the baud rate from the first byte, 0x55
SPI GPIO9 (pin 1) MISO, GPIO10 (pin 2) MOSI, GPIO11 (pin 3) SCK, GPIO12 (pin 4) CS0 Mode 3, up to 10 MHz, 40-bit bootloader datagrams

The driver is built for one bus per object: a port derives from SpiInterface or from UartInterface, never both (a compile-time check, tests/compile_fail/both_buses.cpp).

Control pins¶

The driver drives the control pins only through the optional GpioSet() and GpioGet() hooks of your port, with logical levels; the port maps a level to the physical polarity.

Pin Hook Meaning of the logical level
RSTN (22) GpioSet(CtrlPin::Reset, ...) ACTIVE holds the chip in reset (the pin is low). Used when Config::hardware_reset is set
DRV_EN (21) GpioSet(CtrlPin::DrvEn, ...) ACTIVE allows the gate driver outputs (the pin is high)
WAKE (19) GpioSet(CtrlPin::Wake, ...) ACTIVE asserts the wake condition; only your own power-down logic uses it
FAULTN (20) GpioGet(CtrlPin::Faultn, high) An input: high false means the chip pulls the pin low. Service() reads it

A board that wires DRV_EN high or RSTN to a supervisor leaves GpioSet() out. The driver then cannot drop DRV_EN in DisableDrive(); the chip-side stop (COMMUTATION_MODE 0, or zero enables in register mode) still runs, and the call never fails because the pin hook is missing. Config::hardware_reset without GpioSet() returns Error::Unsupported from EnsureInitialized().

FAULTN is open drain. In the bootloader it signals that the chip is busy bootstrapping or that a severe error stopped the processor (datasheet, Bootloader FAULTN Signaling). In an application it can also pulse when the chip restarts; Config::faultn_is_reset makes Service() treat a low level as a reset (ambiguity A18 in Ambiguities).

Bus settings¶

Setting Bootloader SPI TMCL SPI Register-mode SPI UART (all three)
Mode 3 3 3 8N1
Clock Up to 10 MHz Up to 10 MHz Up to 10 MHz Autobaud after 0x55; 115200 is a safe start
Bit order MSB first MSB first MSB first LSB first, standard UART
Frame 5 bytes 8 bytes, two transfers 6 bytes 8 bytes (bootloader), 9 bytes (TMCL, register)
Chip select Low for each frame Low for each frame Low for each frame -

Every SPI exchange is one Transfer() call with chip select low for the whole frame. The TMCL SPI reply arrives in the transfer after the command, so a command costs two transfers (see Parameter mode).

The MISO line stays driven after chip select rises (erratum 2)

The TMC9660's SPI peripheral does not return MISO to high impedance when chip select is released. With other SPI devices on the same MISO line, hold the chip in reset during their transfers or add the switch the datasheet shows (Errata, Erratum 2). The driver cannot detect this, and GpioSet(CtrlPin::Reset, ...) is the hook for the first workaround.

Timing¶

Parameter Value Driver
Power-up or wake to a ready application, self-test on 44 ms typical Config::boot_timeout_ms (500 ms: the datasheet gives a typical value only, A9)
Same, self-test off 10.5 ms typical The same wait
Wait after a write that reconfigures the chip not specified Config::settle_us (20 ms, A13)
Gap between a TMCL SPI command and its reply request not specified Config::spi_gap_us (1 ms)
UART reply wait not specified Config::reply_timeout_us (50 ms)

The driver waits with your port's DelayUs(); nothing in it sleeps or spins on a clock of its own.

Power¶

Rail Range Note
VSA 7.7 V to 80 V Core and buck supply; the WAKE pin may be shorted to it
VS 7.7 V to 70 V Gate driver supply
VCC_IO 2.5 V to 5 V (3 V or more for SPI at 10 MHz) Logic levels of the GPIO and of the host link
VEXT1, VEXT2 5.0 V, 3.3 V or 2.5 V Outputs, set in the boot configuration; BlWriteConfig() refuses to change them unless allow_ldo_change is set, because both move at once

Hibernation (PowerDown()) puts everything but the always-on block into reset; the chip restarts after the time given or on a rising edge at WAKE, and the driver reports itself uninitialised until EnsureInitialized() runs again.
